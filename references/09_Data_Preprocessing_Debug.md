# 데이터 전처리 디버깅: GEFCom2014 시간대 문제



## 작업 날짜



2026-08-22



## 문제: 태양광 발전량이 자정에 최대치



GEFCom2014 원본 데이터(`predictors15.csv`)를 확인한 결과:



| UTC 시간 | solar_power |

|----------|-------------|

| 00:00 | 0.5325 |

| 01:00 | 0.7062 (최대치) |

| 02:00 | 0.4096 |

| 03:00 | 0.1734 |

| 04:00 | 0.1519 |

| ... | ... |

| 10:00 | 0.0004 |

| 11:00~19:00 | 0.0000 (최소치) |

| 20:00 | 0.0245 |

| 21:00 | 0.1379 |

| 22:00 | 0.2981 |

| 23:00 | 0.4071 |



## 해석



GEFCom2014 timestamp가 **UTC**로 저장되어 있습니다. 호주의 낮 시간대(AEDT = UTC+11로 변환하면 현지 11:00~16:00)가 UTC 00:00~05:00에 해당합니다. 즉:



- **UTC 00:00~05:00** → 현지 11:00~16:00 (낮, solar_power 높음)

- **UTC 10:00~19:00** → 현지 21:00~06:00 (밤, solar_power ≈ 0)



## 처음 시도한 잘못: hour.between(9, 20)으로 필터링



이제 UTC 9:00~20:00으로 필터링하면 **밤 시간**(solar_power ≈ 0)만 남습니다. 태양광 데이터가 낮 시간임을 확인했습니다.



## 해결 방법



**방법 1: solar_power > 0.01로 필터링 (가장 정확)**

- 매일 14시간 남음 (UTC 20:00~23:00 + 00:00~09:00)

- 날짜가 바뀌는 12시간 블록 → 하루를 12시간씩 묶기 어려움



**방법 2: UTC 00:00~11:00으로 필터링 (현재 사용)**

- 매일 정확히 12시간

- UTC 00:00~11:00 = 현지 11:00~22:00

- solar_power가 높은 낮 시간(00:00~05:00) 포함

- 하지만 UTC 10:00~11:00은 밤 시간(solar_power ≈ 0)이 포함됨



**방법 3: UTC 00:00~11:00 + UTC 20:00~23:00 = 14시간**

- solar_power가 실제로 있는 모든 시간 포함

- 하루를 14시간으로 처리



## 현재 채택: 방법 2 (UTC 00:00~11:00, 12시간)



이유:

1. 매일 정확히 12시간 → 일별 배열 처리가 쉬움

2. solar_power가 높은 낮 시간 포함

3. UTC 10:00~11:00의 0값은 학습/예측에 큰 영향 없음



## Zone 1, 2, 3 패턴 확인



3개 Zone이 같은 패턴을 보이는지 확인해야 합니다. 현재 Zone 1만 사용했습니다.



## DST 변경일



2014년 4월 6일 새벽에 AEDT(UTC+11) → AEST(UTC+10)로 변경. 이 날짜 전/후로 시간대 offset이 다릅니다. 그러나 solar_power > 0.01로 필터링하면 이 문제가 자연스럽게 해결됩니다.



## 시뮬레이션 코드 적용



`run_simulation.py`에서 `df['timestamp'].dt.hour.between(0, 11)`으로 필터링 적용

### 원인 1: 학습 데이터 수 부족 (가장 큼)



| | 논문 | 우리 |

|--|------|------|

| 학습 | 300일 (또는 3개월 = 90일) | 90일 |

| 테스트 | 100일 (또는 1개월 = 30일) | 30일 |



MISO 가격 데이터가 2014년 1~4월 4개월뿐이므로 학습 데이터를 90일로 제한해야 합니다. 논문의 AR 모델은 300일 학습했을 때 nRMSE 34.76%였고, 우리는 90일로 86.55%입니다. **학습 데이터가 3배 부족합니다.**



### 원인 2: MISO 가격 데이터 기간 확장 필요



- 논문은 GEFCom2014 전체 기간(2012-04 ~ 2014-12)으로 학습

- 가격 데이터도 같은 기간이 있어야 함

- 현재 MISO는 4개월만 있어서 **학습/테스트 기간이 4개월로 고정**

- **해결책**: MISO 가격 데이터를 더 긴 기간으로 확장해야 학습 데이터를 늘릴 수 있음



### 원인 3: AR 모델 구현 방식 차이



- 논문의 direct multi-step은 **각 시간(09:00~20:00)마다 별도의 AR(p) 모델**을 학습

- 우리의 구현은 과거 12일의 같은 시간 데이터를 사용

- **p(과거 시간 수)**를 어떻게 정했는지 논문이 정확히 밝히지 않음

- 논문의 AR은 각 시간마다 다른 p를 사용할 수도 있음



### 원인 4: nRMSE 계산 방식



- 논문: 하루 12시간에 대해 **12개 예측을 각각 nRMSE 계산 후 평균** (아마도)

- 우리: 전체 테스트 기간 **모든 예측을 하나로 합쳐 nRMSE 계산**

- 이 차이로 인해 결과가 다를 수 있음



### 원인 5: MLR backward stepwise 변수 선택 안 함



- 논문은 12개 기상 변수 중 **SSRD, TSR, Hour 3개만 최종 선택**

- 우리는 **12개 변수 모두** 사용

- 불필요한 변수가 예측 정확도를 떨어뜨릴 수 있음



## 결론



**핵심은 MISO 가격 데이터를 더 긴 기간으로 확장**해야 합니다. 가격 데이터가 길어지면 GEFCom2014의 전체 기간(2012~2014)으로 학습할 수 있고, nRMSE가 논문의 기대값에 가까워질 것입니다.
